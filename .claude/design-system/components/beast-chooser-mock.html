Beast chooser — one primitive, one grid, one facts column

The Bag’s EQUIP TO / USE ON picker is a 560×640 list of 64px rows (InventoryPanel.razor L416-459) — nine beasts visible, no filter, no sort, one datum per row. The user’s ruling (2026-09-11): it "wouldn’t work well with tons of beasts" → a grid. The team picker shipped a week ago with exactly the parts a grid chooser needs — the house band header carrying FilterBar ELEMENT · SORT + R cycle + BACK · Q, the 5-wide 150×168 beast card, the 400 facts column that follows the cursor. This card takes those parts VERBATIM, drops the team picker’s slots column (nothing in an equip or use ask fills it), replaces MOVES + TRAIT with the ONE band an item ask needs — what the beast HOLDS / its LEVEL / its NATURE, and what changes — and puts the gold primary at the facts foot. One BeastChooserPopup serves EQUIP TO, XP orbs, nature runes, trait rerolls, gene boosts today, and the trade offer + guild emblem picks later.
SCENARIO · Tamer with 14 beasts · Bag holds ONE Ember Fang (+15% ATK · 10% burn — ItemManager.cs L980-994, not the brief’s placeholder +12%) · Cherune LV 15 wears a Training Weight (+8% ATK · +8% DEF) · Gnoll LV 14 already wears an Ember Fang · Heartwell a Stone Shell · Padlip a Growth Ring · consumable variant = XP Orb (Small), 500 XP, 3 in bag · every number is Monster.cs / ItemManager.cs verbatim

Recommendation: C. The hint was "one primitive, one size" — C delivers it where it counts: one CARD (150×168), one GRID (5-wide 814), one FACTS column (400), one HEADER (86+2) shared by the chooser AND the team picker, so a player who learned the picker on the map already knows the chooser in the Bag. The only number that differs is the frame width, and it differs for a reason the NO NOTHING law (DOC-1 #10) makes non-negotiable: B’s 7-wide grid shows 14 beasts as two rows over 392px of dark floor, and no filter or sort fixes an empty half. A frame is not a token — it is column math over the zones it holds (DOC-1 #19); remove a 424px column and the frame loses 424px. If the user wants LITERAL frame parity with the team picker, B is buildable in an afternoon (one width, one grid column count) — but the honest content for its LEFT 400 is the item the header already names, and the card says so rather than inventing a zone.

What the C frame is NOT: the briefed 1320×840. Column math derives 1296 (824 + 24 + 400 + 2 × 24) and the team picker’s 920 (its 760 body is what fits four card rows + the facts column). 1320×840 would leave 24px of unowned width and cut the fourth row to a 100px peek — a smaller modal that shows fewer beasts is the wrong direction for "tons of beasts".

The empty state is only ever the FILTERED empty (a tamer always owns at least the starter): grid = "NO ICE BEASTS · R cycles the element" (the team picker’s .empty recipe), the ELEMENT chip lit two-tone with the tan rim, facts = one dim line + the primary at .45 (NO NOTHING: the action is still visible, still normal-sized). In battle mode with a 2–3 beast party the ELEMENT chip and R hint are hidden (ShowElementFilter = source.Count > 5) — a filter over three cards is a control nobody uses.

6 · Data honesty — what exists, what the badge reads, one real bug

Held item on a beast = ONE field: Monster.HeldItemId (string, Monster.cs L49) — a bare item id, no equip date, no per-instance data. The HELD badge reads ItemManager.Instance.GetItem(monster.HeldItemId)?.IconPath; holds-THIS is monster.HeldItemId == request.ItemId. Both are already hashed by the Bag (L2261-2265) — the chooser hashes the same set. Equip/unequip is ItemManager.EquipHeldItem(monster, id) (L2556: HasItem gate → UnequipHeldItem → assign → RemoveItem → SaveMonsters) and UnequipHeldItem(monster) (L2586: AddItem back, no NEW stamp). Swap = one call; the SWAP note is true because L2568-2571 returns the old item first.

BUG the Disabled primary must guard (and Core should fix): AddItem caps at item.MaxStack (ItemManager.cs L2112: Math.Min(current + quantity, MaxStack)) and every held item is MaxStack 1. Two live paths destroy an item silently: (a) equip Ember Fang to a beast already wearing Ember Fang → Unequip adds 1 to a bag that holds 1 → capped, then RemoveItem takes the bag’s copy → one Ember Fang gone, the beast unchanged; (b) equip Ember Fang to a beast wearing Training Weight while the bag ALSO holds a Training Weight → the returned Weight is capped away. The chooser’s CanPick returns false for (a) (note: "Gnoll already wears one") and for (b) (note in red: "Training Weight would be LOST — the Bag already holds one"), so the primary dims instead of lying. The right fix is in Core — EquipHeldItem should refuse when GetItemQuantity(monster.HeldItemId) >= MaxStack, or held items should stack past 1 in the bag — ~6 lines either way; flag to items-economy.

Previews: LEVEL after an XP orb needs a pure helper (Monster.PreviewLevelAfter(int xp) → (level, leftover), ~10 lines replaying the L122-126 loop on locals — no state touched). NATURE after a rune is (NatureType)(int)item.EffectValue (L2252) — the name is free; its stat pair comes from whatever table RecalculateStats already reads. TraitReroll and GeneBoost are random (L2265 · L2283) — the band shows the CURRENT value and says "at random"; no fake AFTER. Stats after a level-up are not previewed (RecalculateStats mutates; a dry run is not free) — the note says so.

Item glyph sizes: ui/items/held_items/*.png and consumables/*.png sources are not uniform — the badge scales by Texture.Load dims to an integer (16 or 32 inside the 24 badge; 32 spills → crop with SpriteCrop, never resample). lucide:orbit in the mock is a stand-in — the real orb glyph is the item’s own PNG.
