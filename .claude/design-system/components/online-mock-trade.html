Online mock — trade offers as shipped

An offer says everything in one line: the beast they WANT, the beast they'll give FOR it, who posted it, when. The hub zone shows the newest three; VIEW ALL OFFERS opens the board — a filterable card grid of every posted offer. Accepting an offer whose poster is online opens the existing trade window; offline posters wait for the server board (async with escrow — the future section below). No free text anywhere; every slip reads the same.

Keyboard — the board's cursor space

  • 0 POST OFFER (ring host, default r24) · 1..4 filter chips (in the header — slab cursor) · 5+ cards (slab cursor, BoardCols 3). Lands on the first card (else POST OFFER) on open.
  • Vertical order on screen = chips ↑ · POST OFFER · cards ↓ (re-routed when the chips moved into the header — a route that contradicts the screen is a bug). POST OFFER: W → the active chip · S → card 0. Chips: A/D between chips · S → POST OFFER · Space selects. Cards: A/D within the row · W/S ±3 · W off row 0 → POST OFFER · Space / Enter / E accept.
  • R cycles the filter anywhere · Q → BackToHub (PanelHandledBackKey claimed; the board branch runs BEFORE the generic takeover block in TickInput).
  • Scroll-follow: every cursor move arms `_boardFollowPending`; Tick consumes it via UiGridScroll.ComputeIndexOffset + the roster 0.30 glide; a cursor on the band / filters glides the grid to the top.

Future — the server board: async with escrow (NOT shipped)

USER RULING 2026-08-28, unchanged: standing offers are ASYNC WITH ESCROW. The poster's side is held server-side at post time; the acceptor's side at accept; both delivered through the EXISTING gift-claim pipeline on next login. No live handshake — an accept is final. This is what fills `HubOffers` in production and what makes an OFFLINE accept possible. Everything below is spec, not code.
POSTComposer → POST OFFER. Your FOR beast leaves your roster into server escrow immediately. Offer lists for 48h whether or not you stay online.POST /board · escrow poster side
ACCEPTAny tamer presses ACCEPT (confirm dialog). Their WANT-side beast goes into escrow at that moment. The offer leaves the board — an accept is final.POST /board/{id}/accept · validate + escrow acceptor side
DELIVERBoth deliveries queue through the EXISTING gift-claim pipeline: the acceptor gets the poster's beast on their next login; the poster gets the acceptor's on theirs.gift-claim pipeline, unchanged
RETRACT / EXPIREREMOVE, or 48h passes with no accept → escrow returns to the poster via the same gift-claim route. No orphaned beasts, ever.DELETE /board/{id} · server expiry sweep
ANTI-ABUSE CAPS · one active offer per tamer (posting again replaces) · 48h expiry auto-return · N accepts per day · post rate-limit · no self-accept · both sides ownership-validated server-side before escrow · GET /board is server-filtered for expiry, client-filtered for unresolvable species (the bag ghost-item lesson) · client-side additions when it lands: a "46H LEFT" time chip beside time-ago, REMOVE on YOURS cards, "Offer no longer available" dim state on a card that resolved mid-view
